# 04 · Хостинг

Уровень: физический. Отвечает на вопрос «как приложение доступно с телефона».

**В базе — только локальная сеть.** Внешний доступ отложен (решение №1 в
`08-развилки.md`): ни домена, ни туннеля, ни проброса портов. Телефон подключается
к BFF по адресу машины в домашней сети.

## Что это значит на практике

```
телефон (Wi-Fi дома) → http://192.168.178.43:8080 → BFF на hermeshome
```

- BFF слушает `0.0.0.0:8080` — доступен всем в локальной сети, не только с самой машины.
- Адрес машины в сети меняется при перезагрузке роутера (DHCP). Решение: имя хоста
  `hermeshome.local` + fallback на текущий IP; в клиенте — поле адреса, запоминает
  последний рабочий.
- Вне домашней сети приложение недоступно. Это осознанно: база делается локальной,
  внешний доступ — отдельная задача.

## HTTPS: нужен для service worker

**Service worker работает только на HTTPS или localhost.** По обычному HTTP
с телефона браузер его не зарегистрирует — приложение откроется, но офлайн
не заработает: ни кэш оболочки, ни «страница открылась без сети».

Это ограничение браузера, а не выбор. Варианты:

| | Как | Офлайн | Заметки |
|---|---|---|---|
| HTTPS с самоподписанным сертификатом | BFF за TLS на своём порту | да | Телефон спросит доверие один раз, предупреждение останется |
| localhost через туннель | Туннель ведёт телефон на `127.0.0.1` | да | Service worker разрешён, но туннель — отдельная настройка |
| Обычный HTTP | как сейчас | нет | Приложение работает, очередь команд в IndexedDB — тоже, но без service worker |

**Решение (01.11.2026): HTTPS поднят на порту 8443.** BFF отвечает и по HTTP
(`8080`), и по HTTPS (`8443`) — это два процесса: `coach-app.service` и
`coach-app-tls.service`. Порт 443 занять нельзя без sudo, а PWA работает на
любом HTTPS-порту.

Сертификат — локальный CA (mkcert) на имя `192.168.178.43`, `192.168.178.44`,
`localhost`, `127.0.0.1`. Файлы лежат в `~/.local/share/coach-app/tls/`
**вне репозитория**: приватный ключ CA в git попадать не должен.

### Установка на телефон

Chrome на Android не считает `192.168.x.x` безопасным: без HTTPS он не
предложит «Установить приложение». С HTTP-адреса установка невозможна.

Порядок на телефоне (один раз):

1. Открыть `http://192.168.178.43:8080/ca.crt` — сертификат CA скачается.
   Android спросит, откуда; выбрать «Настройки» и поставить.
2. Android 7+ требует для установки CA разблокировки экрана:
   Настройки → Безопасность → Шифрование и credentials → Установка сертификата
   → «Сертификат CA пользователя».
3. Открыть `https://192.168.178.43:8443/` — предупреждение исчезнет, когда
   телефон будет доверять CA.
4. Меню Chrome → «Установить приложение» (или «Добавить на главный экран»).

**Проверка отпечатка CA.** Файл сертификата можно сверить с отпечатком на
машине — так исключена подмена сертификата:

```
openssl x509 -in ~/.local/share/coach-app/tls/ca.pem -noout -fingerprint -sha256
```

**Путь без ручной установки CA** — сертификат от публичного CA по
настоящему домену (Let's Encrypt). Тогда телефон доверяет из коробки и ничего
ставить не надо. Это отдельная задача: нужен домен и его DNS.

### Условия установки PWA

Chrome проверяет четыре вещи. Все должны выполняться одновременно:

| Условие | Где |
|---|---|
| HTTPS (или localhost) | `coach-app-tls.service` на 8443 |
| Манифест с `name`, `start_url`, `display: standalone` | `client/manifest.json` |
| Иконки 192×192 и 512×512 (+ maskable для Android) | `client/icons/`, рисует `tools/render_icons.py` |
| Service worker с обработчиком `fetch` | `client/sw.js` |

Иконки рисуются кодом, а не хранятся готовыми: палитра живёт в
`client/style.css`, и иконка обязана быть из неё же. `python3 tools/render_icons.py`
перерисовывает их после правки палитры.

## Кэширование статики: почему `Cache-Control: no-cache`

**Статика отдаётся с `Cache-Control: no-cache`.** Без этого заголовка телефон
по обычному HTTP (service worker не работает) держит `app.js` в браузерном
кэше и показывает старую версию клиента: правка в коде есть, а на экране её
нет. Выглядит как «приложение сломалось», хотя сервер отдаёт свежий код.

`no-cache` — не «не хранить», а «уточни у сервера перед использованием»:
`ETag` и `Last-Modified` остаются, трафик не растёт.

## Кэш service worker'а: network-first, а не cache-first

**Оболочка берётся из сети, кэш используется только офлайн.**

При cache-first worker отдаёт кэш **всегда**, а обновление уходит в фон.
Из-за этого правка в коде не доезжает до экрана: телефон берёт старый `app.js`
из кэша worker'а, и приложение выглядит сломанным. В инкогнито, где worker'а
нет, работало — отсюда разница между профилями браузера.

Три уровня устаревания кода, и каждый надо пройти:

1. **Заголовок ответа** — `Cache-Control: no-cache` на статике.
2. **Service worker** — оболочка из сети (network-first), сам `sw.js` — тоже
   из сети, иначе новая версия worker'а не установится никогда.
3. **Открытая страница** — старый `app.js` уже в памяти браузера. Кнопка
   «обновить» в шапке не только перезапрашивает данные, но и переоткрывает
   страницу с меткой `?v=<время>` — без этого правка в коде не дойдёт до
   экрана.

**Проверка: смотри, что лежит в кэше worker'а.** «У меня работает» в браузере
на `localhost` ничего не значит: там worker есть, а на телефоне по HTTP — нет.
Проверять надо оба пути.

## Доступ

**В базе нет ни HTTPS, ни авторизации.** Решение Кирилла (26.10.2026): аутентификацию
и авторизацию добавим позже.

Риск, который это создаёт: любой в домашнем Wi-Fi получает доступ к плану и факту.
Осознанно принят на старте. Смягчение, если понадобится: BFF слушает `127.0.0.1`,
и тогда достучаться можно только с самой машины.

Когда появится внешний доступ, обязательными станут **и** HTTPS, **и** авторизация —
иначе данные и любой будущий токен улетят открытым текстом через интернет.

## Firewall: порты, которые должны быть открыты

**ufw на машине: политика INPUT — DROP.** Правила, без которых телефон
не достучится:

```
8080/tcp  ALLOW  192.168.178.0/24   # coach-app LAN (HTTP)
8443/tcp  ALLOW  192.168.178.0/24   # coach-app HTTPS (PWA install)
```

Правила лежат в `/etc/ufw/user.rules` и переживают перезагрузку.

**Питфалл — порт в приложении, но не в firewall.** Сервис поднят, порт
слушается, `curl` с самой машины отвечает 200 — а с телефона «ничего не
работает». Причина: ufw отбрасывает SYN, потому что правила для порта нет.
Проверяется так:

```
sudo journalctl -k --since "10 min ago" | grep "UFW BLOCK" | grep DPT=8443
```

Строка `SRC=<телефон> ... DPT=8443 ... SYN` означает: пакет дошёл до
машины и был отброшен брандмауэром, а не приложением.

## Условия на этой машине

Проверено на хосте `hermeshome`:

- IPv4 `192.168.178.43` — адрес в домашней сети, по нему телефон ходит на BFF.
- `wg` установлен, `wg show` пуст — своего туннеля нет.
- `tailscale` и `cloudflared` — нет.
- `sudo` без пароля нет; есть `systemctl --user`.
- Пользователь в группе `docker`.
- Пользовательские сервисы systemd работают: `coach-app.service` активен.

Для локальной сети достаточно двух вещей: BFF слушает локальный адрес и пользовательский
сервис с автозапуском. Ни sudo, ни туннели, ни права на роутере не нужны.

## Процессы

```
systemd --user:
  coach-app.service    BFF (uvicorn), restart=on-failure
```

Пользовательские сервисы systemd работают на этой машине — автозапуск и перезапуск при
падении получаются без sudo и без системного root.

Файл сервиса:

```
~/.config/systemd/user/coach-app.service

[Unit]
Description=Coach App BFF
After=network-online.target

[Service]
ExecStart=<путь>/.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8080
Restart=on-failure
RestartSec=5

[Install]
WantedBy=default.target
```

## Конфигурация

**Факт:** каталога `~/.config/coach-app/` нет. Приложение запускается с переменной
окружения `COACH_APP_DATA` (путь к данным) и без всякой конфигурации: порт и хост
заданы в файле systemd-сервиса `deploy/coach-app.service`.

Планировалось `~/.config/coach-app/config.toml` (порт, хост, путь к данным, режим
деградации) и `token` (`chmod 600`). Секретов в хранилище не лежит.

## Что доступно наружу

За пределы домашней сети — ничего. Наружу не выходит ни домен, ни Garmin, ни нарратор,
ни хранилище. Приложение отдаёт только то, что пользователь запрашивает у себя:
план и факт.

## Что отложено и вернётся позже

| Отложено | Когда вернётся |
|---|---|
| Внешний доступ (домен, HTTPS, туннель) | Когда понадобится доступ извне дома |
| Настоящая аутентификация | Когда появится второй пользователь или другие клиенты |
| Проброс портов на роутере | Вместе с внешним доступом |

Варианты внешнего доступа разобраны заранее — см. предыдущую редакцию этого файла
в истории git (`git log -- v2.architecture/design/04-хостинг.md`): A · Cloudflare Tunnel
рекомендован как основной, B · Tailscale как запасной, C · WireGuard вручную и
D · IPv6 напрямую — не включать.

## Риски

| Риск | Что делаем |
|---|---|
| Любой в домашнем Wi-Fi угадает адрес | Риск принят осознанно: авторизация позже. Сейчас — доступ всем в сети |
| Адрес машины сменился | `hermeshome.local` + ручной ввод адреса в клиенте, запоминает рабочий |
| Приложение упало | `Restart=on-failure` + `RestartSec=5` |
| Данные на диске дома | Бэкап хранилища по расписанию не настроен (см. `02-хранилище.md`) — риск принят осознанно |
