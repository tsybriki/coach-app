2 · Схема

Уровень выше доменной модели. Домен отвечает на вопрос «что за сущности», этот уровень — «кто какое решение принимает». Всё, что связано с размещением, хранением и протоколами, вынесено из картинки: это следующий уровень.

источники — поставляют данные, ничего не решают принимают решения наблюдают и считают итог граница с пользователем сквозной слой решений

Полосы — подсистемы, стрелки — кто у кого берёт. Показано 11 связей из 12; не показана одна: внешние источники → факт (чип на полосе «Факт»). Номер у стрелки = номер строки в таблице «Взаимодействия».

3 · Планировщик

Планировщик — единственная подсистема, которая принимает решения. Четыре шага: вердикт по достижимости, макро, неделя, остаток недели.

1Шаг 1 · ДОСТИЖИМОСТЬ
  1. Нормализовать цель: метрика + дата → целевой VDOT (Дэниэлс: 10К 40:00 → VDOT 52).
  2. Оценить текущую форму: факт 10К 44:06 → VDOT 46.4, тренируемся по 48. Разрыв 4–6 VDOT.
  3. Взять из методологии правило роста формы и оценить потолок к дате цели.
  4. Вердикт: достижима · достижима с оговорками · недостижима.
  5. При недостижимости — варианты: смягчить метрику · сдвинуть дату · наилучшая достижимая цель.
  6. Согласовать цель с пользователем — вердикт без согласия в макро не идёт.
вход Goal (метрика + дата) + Профиль атлета + правило роста формы из методологии
цифры Цель 10К 40:00 = VDOT 52 · факт 10К 44:06 = VDOT 46.4 · тренировочный 48 · гонка 18.04.2027 = W28 из 49
есть goal_guard.py проверяет согласованность плана с целью — но не достижимость цели из текущей формы.
нет Правило роста формы — заглушка: пока оно пустое, вердикт честно отвечает «не могу оценить». Шаг 6 — генератора макро нет: weekly_macro (28 недель из 49) написан руками.
2Шаг 2 · МАКРОПЛАН
  1. Построить Plan: фазы, weekly targets, load budget, control points.
  2. Проверить, что недельные цели не превышают бюджет нагрузки.
  3. Проверить, что race-pace блок выходит на темп цели.
  4. Записать макро как состояние: версия, чтобы изменения были видны.
вход согласованная цель + макро-правила из методологии
цифры weekly_macro покрывает 28 недель из 49 — написано руками
есть goal_guard.py — проверка согласованности макро с целью.
нет Генератора макро нет: макро пишется руками, а не считается.
3Шаг 3 · НЕДЕЛЯ
  1. Взять цель и объём недели из макро.
  2. Выбрать структуру качественной сессии по (goal, scale).
  3. Разложить по слотам календаря.
  4. Что не разложилось — в unplaced: висяк, решение пользователя.
  5. Собрать шаги; длительность тренировки = Σ шагов.
  6. Неделя готова к активации — активация по команде пользователя.
вход макро (weekly target недели) + Профиль атлета + Среда (слоты)
цифры работает: plan_generate · step_builder · quality_session · workout_templates
есть lib/plan_generate.py + lib/step_builder.py + lib/quality_session.py + state/workout_templates.json — этот вход собран и работает.
нет Наследование слотов Season ← Phase ← Week не реализовано: слот берётся только из constraints.json.
4Шаг 4 · ОСТАТОК НЕДЕЛИ
  1. Пересобрать сессии на сегодня и позже, прошедшие не трогать.
  2. Отдать diff с последствиями и предупреждениями.

Планирование (2)
граница
Не знает о тренировках и целях. Доступность ресурса — во времени, а не «навсегда». Календаря нет: доступность задаётся здесь, а не подтягивается извне.
Методология src

решает
Ничего не решает: правила задают, что считать, движок — как считать. Выбор внутри заданных правил — решение Планирования.

Планирование (3)
граница
Не знает ни атлета, ни цели, ни календаря. Правила и движок работают с любым входом. Новую методику нельзя добавить, не тронув код. Правило роста формы на старте — заглушка.
Планирование decide

строит тренировочный процесс: вердикт по достижимости → макро → неделя → остаток недели

решает
Как распределить нагрузку и тренировки по фазам, неделям и слотам. Достижима ли цель — по правилу роста формы, взятому из методологии. Что не разложилось — висяк, решение пользователя.
владеет
Goal, Plan (фазы, недельные цели, бюджет нагрузки), Week (запросы → размещения → тренировки → шаги), вердикт по достижимости, diff остатка недели

6 · Куда это ложится физически

Куда каждая логическая подсистема может ложиться физически. Это следующий уровень — здесь только раскладка, решения не приняты.

Атлетсервер, состояние + кэш в клиенте
Средасервер + кэш в клиенте

7 · Развилки
1. Достижимость — отдельная подсистема, шаг внутри Планирования или функция методологии?
A — Функция методологии.
B — Отдельная подсистема со своим входом и выходом.
что меняет: Решено: функция методологии. Правило роста формы живёт в методологии, вердикт считает планировщик. Отдельной подсистемы «Цель и достижимость» больше нет — в плане остаётся шаг 1.
2. Где граница между правилами методологии и кодом, который их применяет?
A — Движок внутри Планирования: методология — данные, код чтения правил живёт в планировщике.
B — Движок отдельно: свой слой «правила + исполнитель» → результат.
что меняет: Решено: A. Новая методика всегда требует кода. Простота важнее гибкости: отдельного исполнителя нет.
3. Факт — одна подсистема с Оценкой или две?
A — Две: Факт принимает и нормализует, Оценка связывает с планом и считает итог.
B — Одна: приём, связывание и подсчёт — вместе.
что меняет: Решено: A. Граница с внешними источниками остаётся чёткой: приём Garmin — адаптер, а не часть логики.
Замечания по текущему состоянию
Достижимость — функция методологии: правило роста формы в методологии, вердикт считает планировщик. Пока правило — заглушка, вердикт честно отвечает «не могу оценить».
Достижимость (шаг 1) и переплан остатка (шаг 4) не реализованы: модели потолка формы нет, генератора макро нет, переплан возвращает пустой diff.
Макро в данных покрывает 28 недель из 49 и написано руками — то есть сегодня его нет как результата работы подсистемы.
Связь план↔факт зафиксирована в домене (Workout.actual_id ↔ ActualSession.linked_workout_id), но в данных её нет ни в одной таблице state.
Диаграмма DOMAIN-SPEC.html подписывает блок факта как «Garmin / Stryd / TrainingPeaks» и содержит строку «поздно пришедшая активность меняет закрытую неделю» — обе расходятся с подтверждёнными I14 и I23.
Google Calendar не подключается: доступность тренировок — дефолтные слоты и инвентарь в подсистеме «Среда», версионируемые как обычное состояние.
Данные Stryd отдельно не грузим: берём то, что Stryd складывает в Garmin. Нагрудный ремень используется на важных тренировках — данные идут через Garmin.
