Принципы

  1. Решения принимает код. LLM только формулирует. Числа считает домен.
  2. Ничего не инициируется само. Любое изменение состояния — команда от пользователя.
  3. Источник правды один. Производное пересчитывается, а не хранится вторым экземпляром.
  4. Логика не знает о формате хранения. Доступ к данным — только через порты;

формат (файлы, база) знает только адаптер. Проверяется чекером, не договорённостью.

  1. Деградация вместо отказа. Упавший внешний источник ограничивает, но не роняет.
  2. Один пользователь. Ничего не строим на будущее, чего этот пользователь не делает.
  3. Заглушка честнее выдумки. Нет правила — «не могу оценить», а не выдуманное число.

Контракты01-контракты.md

Уровень: контрактный. Отвечает на вопрос «как подсистемы общаются».

Команда — единственный способ изменить состояние

Ничего не меняется само: ни закрытие недели, ни связывание факта, ни статус тренировки.

Command {
  id              string      # идемпотентности, генерирует клиент
  type            enum        # см. ниже
  target          object      # {week_id?, actual_id?, workout_id?}
  args            object      # payload по типу команды
  reason          string      # обязателен, пустой не принимается
  issued_at       datetime
  issued_by       enum        # user | brain
  expected_version int        # версия состояния, на которой клиент строил команду
}

Типы команд

Пустых мест быть не должно: каждая операция, меняющая состояние, — команда.

Загрузка факта

Тип Что делает args
pull_fact вытянуть активности из Garmin за период {from, to?, sport?}

Без pull_fact связывание не работает. Факт живёт вне плана и появляется только через

загрузку: сначала pull_fact — в хранилище появляются ActualSession без плановой пары,

потом link_actual связывает конкретную сессию с тренировкой. Без загруженного факта

связывать нечего — интерфейс выбора факта пуст.

Ответ pull_fact содержит, что именно пришло: pulled[] — новые сессии, skipped[] —

уже загруженные (тот же external_id), degraded — источник недоступен.

Неделя

Тип Что делает args
propose_week макро → неделя {season_week}
activate_week proposed → active {season_week}
close_week active → closed + саммари {season_week}
replan_remainder пересборка сессий на сегодня и позже {season_week, trigger}
place_unplaced висяк → слот {request_id, slot_id, start}
unplace_request размещённая тренировка → обратно в висяки {request_id}

Факт и связь

Тип Что делает args
link_actual факт ↔ тренировка {workout_id, actual_id}
unlink_actual разрыв связи {workout_id}
edit_actual поправить факт вручную {actual_id, patch}

edit_actual — для ручного факта (source: manual): Garmin не знает про силовую с

дистанцией «0 км» или про ОФП. Факт без Garmin-записи всё равно должен попадать в отчёт.

Профиль и цель

Тип Что делает args
update_athlete профиль атлета {patch}
set_goal новая цель плана {goal}
set_plan макроплан: фазы, недельные цели {plan}

Среда

Тип Что делает args
set_slots базовые окна тренировок {slots}
override_slots перекрытие слотов фазы или недели {scope, scope_id, ops[], reason}
set_equipment реестр оборудования {equipment}

Гейты (контрольные точки)

Тип Что делает args
set_gate_result значение проверки контрольной точки {gate_id, check_id, value, note?}
decide_gate решение по контрольной точке {gate_id, decision, note?}

set_gate_result — записать измеренное значение (время на 3К, темп). decide_gate —

решение пользователя: «идём по плану» или «корректируем». Два разных шага: первое —

факт, второе — намерение. Автоматика считает значения, но решение — за человеком.

Служебное

Тип Что делает args
narrate получить текстовое объяснение {about, diff?}
import_state первичный импорт состояния {source}
import_fit загрузить FIT-файл и разобрать метрики {path?, pull_days?}

narrate — единственная команда, которая не меняет состояние. Она возвращает текст,

не считает и не применяет.

brain не инициирует команды сам. Он готовит предложение — тот же конверт с issued_by: brain —

и ждёт подтверждения пользователя.

Что было упущено и почему это важно

Команда Без неё Что ломается
pull_fact факта нет в системе связывание невозможно; отчёт всегда пустой
edit_actual ручной факт невозможен силовые и ОФП не попадают в отчёт
set_gate_result результат гейта некуда записать контрольные точки — только чтение
decide_gate решение по гейту некуда записать решение пользователя теряется
import_fit FIT не загрузить нет детальных метрик: каденс, дрейф, тренировочный эффект
override_slots перекрытие слота только вручную в файле наследование Season ← Phase ← Week не работает
set_slots базовые окна меняются правкой файла доступность тренировок не управляется из приложения
set_plan макроплан меняется правкой файла фазы и недельные цели не управляются
unplace_request висяк нельзя вернуть в висяки ошибку раскладки не исправить
set_equipment реестр оборудования меняется правкой файла ограничения по оборудованию не управляются

Ответ на команду

CommandResult {
  status       enum        # applied | rejected | needs_confirmation
  new_version  int
  diff[]       object      # что поменялось: {path, before, after}
  consequences object      # {scope: local|ripple|season, affected[]}
  warnings[]   string
  error        object?     # {code, message, field?}
}

needs_confirmation — команда применена только частично или задевает следующие недели

либо сезон. Пока пользователь не подтвердил, применённая часть — уже в состоянии,

а остальное отложено.

Идемпотентность

id команды пишется в журнал. Повтор с тем же id возвращает тот же CommandResult

и не применяет команду второй раз. Это позволяет клиенту ретраить outbox не глядя.

pull_fact — частный случай: повторный вызов с тем же периодом не создаёт дублей

(external_id уникален), а возвращает skipped[] для уже загруженных.

Конкуренция

expected_version не совпал с текущим → команда отклоняется, ответ status: rejected,

error.code = version_conflict, в ответе — текущий снапшот, чтобы клиент переспросил.

Порты — контракты внешнего мира

Логика знает только эти интерфейсы. Реализации — в адаптерах.

Порт Ответственность Поведение при сбое
SeasonRepo состояние сезона: план, фазы, недели отказ при устаревшей версии
FactRepo факт: чтение, добавление, связывание дубликат external_id → отказ с кодом
AthleteRepo профиль атлета нет профиля → пустой профиль, не ошибка
MethodologyRepo правила: модели, шаблоны, шкала зон нет правил → пустой набор, не ошибка
CommandLog журнал команд: идемпотентность повтор команды → тот же результат
ActivityPort вытянуть активности из внешнего источника таймаут + retry + деградация
NarratorPort текст, варианты, объяснения нет ключа → детерминированная заглушка
Clock текущее время в тестах — фиксированное
IdGen идентификаторы детерминированный в тестах

Первые пять — порты хранения. Их сигнатуры описаны в 02-хранилище.md.

Ни один порт не упоминает формат хранения: нет параметров path, table, query.

Правила ошибок

  1. Код ошибки + человеческое сообщение. Без стектрейсов в ответе.
  2. Внешний источник недоступен → команда, которая от него зависит, отклоняется с degraded,

остальные работают.

  1. Битые входные данные (пустое значение, невалидный объект, отсутствующее поле) → понятное

сообщение и безопасное поведение, не исключение.

  1. Доменная ошибка (нарушен инвариант) → команда отклоняется, состояние не меняется,

в warnings — что именно нарушено.

  1. pull_fact при недоступном Garmin → rejected с degraded, pulled[] пуст.

Планирование при этом не затронуто.

Хранилище02-хранилище.md

Уровень: физический. Отвечает на вопрос «где состояние лежит и как пишется».

Принцип: физическое хранилище знает только адаптер

Никто, кроме адаптера хранилища, не знает, что состояние лежит в файлах, в базе данных или

где-либо ещё. Домен, сервисы, BFF и клиент работают только через интерфейсы.

Это значит:

  • домен не импортирует sqlite3, json, os.path — ему не нужно;
  • сервисы не знают, есть ли база;
  • BFF не знает, как хранится состояние — он знает только порты;
  • клиент не знает, откуда пришли данные.

Смена хранилища — замена одного файла в adapters/. Ничего больше не меняется.

Правило проверяется, а не декларируется

python3 tools/check_storage_leaks.py

Чекер проходит по коду и по дизайн-документам и падает, если вне adapters/storage/

появилось знание о формате хранения: sqlite3, json.dump, read_text, os.replace,

flock, пути к файлам, .json. Команда обязана быть в CI: зелёный чекер — условие коммита.

Эталон: v2.architecture/check_storage_leaks.py в репозитории ~/coach.

Путь развития

Сейчас — файлы. JSON, один файл на корень агрегата. Данных мало, писатель один,

нужен diff в git и читаемость руками.

Потом — база данных. SQLite. Переход спланирован заранее: контракты портов не меняются,

меняется только реализация и добавляется шаг миграции данных.

Критерий перехода, зафиксированный заранее, чтобы не спорить позже:

Триггер Почему он важен
Второй писатель (клиент пишет напрямую, или два процесса) Файловая блокировка перестаёт быть достаточной
Нужны запросы по произвольным полям (все факты за период, все пропущенные за сезон) Файлы требуют читать и фильтровать в коде
Состояние перестало помещаться в память целиком Читать всё для одного экрана — дорого
Нужна транзакция между несколькими сущностями Файлы дают атомарность на файл, а не на набор

Пока ни один триггер не сработал — файлы. Когда сработает — переход по процедуре ниже.

Схема доступа: интерфейсы

Доступ к данным — только через эти интерфейсы. Они объявлены в ports/, реализуются

в adapters/.

class SeasonRepo(Protocol):
    """Состояние сезона: план, фазы, недели, журнал команд."""
    def load(self) -> SeasonState: ...
    def save(self, state: SeasonState, expected_version: int) -> int: ...
    def week(self, season_week: int) -> Week | None: ...
    def put_week(self, week: Week, expected_version: int) -> int: ...
class FactRepo(Protocol):
    """Факт: выполненные сессии."""
    def list_for_week(self, season_week: int) -> list[ActualSession]: ...
    def list_in_range(self, start: date, end: date) -> list[ActualSession]: ...
    def get(self, actual_id: str) -> ActualSession | None: ...
    def upsert(self, session: ActualSession) -> ActualSession: ...
    def link(self, actual_id: str, workout_id: str | None) -> None: ...
class AthleteRepo(Protocol):
    """Профиль атлета."""
    def get(self) -> Athlete: ...
    def update(self, athlete: Athlete) -> None: ...
class MethodologyRepo(Protocol):
    """Правила методологии: PlanModel, LoadModel, шаблоны, шкала зон."""
    def plan_models(self) -> list[PlanModel]: ...
    def load_model(self) -> LoadModel: ...
    def workout_templates(self) -> dict: ...
class CommandLog(Protocol):
    """Журнал команд: идемпотентность."""
    def get(self, command_id: str) -> CommandResult | None: ...
    def append(self, command: Command, result: CommandResult) -> None: ...

Правило: ни один метод интерфейса не упоминает формат хранения. Нет параметров

path, table, collection, query. Всё — на языке домена: season_week, actual_id,

expected_version.

Что достаточно для текущих задач

Операция Интерфейс Где используется
Прочитать сезон целиком SeasonRepo.load проекции для клиента
Прочитать одну неделю SeasonRepo.week экран недели
Сохранить неделю SeasonRepo.put_week propose / activate / close / replan
Сохранить сезон SeasonRepo.save новая цель, смена плана
Факт за неделю FactRepo.list_for_week связывание, саммари
Факт за период FactRepo.list_in_range отчёт за сезон, год
Одна сессия FactRepo.get карточка тренировки
Записать сессию FactRepo.upsert вытягивание из Garmin
Связать с планом FactRepo.link link_actual / unlink_actual
Профиль AthleteRepo всё планирование
Правила MethodologyRepo планировщик, нагрузка
Журнал CommandLog идемпотентность

Интерфейсов достаточно. Не хватает двух вещей, и они добавлены:

  1. FactRepo.list_in_range — запрос за период. Без него отчёт за сезон требует

чтения всех недель и фильтрации в коде. В файловом хранилище это работает,

в базе — это запрос. Добавлен именно поэтому: дешевле предусмотреть сейчас.

  1. SeasonRepo.week — точечное чтение недели. Без него клиент тянет весь сезон,

чтобы показать одну неделю.

Текущая реализация: файлы

data/
  season.json            Season · Plan · Phase · журнал Command
  athlete.json           профиль атлета
  weeks/W<n>.json        Week · requests[] · assignments[] · workouts[] · steps[] · summary
  actual/W<n>.json       ActualSession[] за неделю
  methodology/           PlanModel · LoadModel · шаблоны тренировок · шкала зон
  versions.json          текущая версия схемы + применённые миграции

Имена — от домена: athlete.json, а не athlete_json_file.json. Неделя разбита по файлам,

чтобы размер не рос с сезоном и неделю можно было отдавать в клиент поштучно.

Версия схемы и миграции

  • data/versions.json: {"schema_version": 3, "applied": ["0001_initial", "0002_week_files"]}.
  • Миграции — код в migrations/, по одной на версию, идемпотентные.
  • При открытии текущая версия сравнивается с целевой, недостающие миграции применяются

по порядку. Миграция падает — данные не трогаются, процесс не стартует.

  • Миграции только вверх. Откат — восстановление из бэкапа.

Атомарная запись

запись: 1. во временный файл в том же каталоге
        2. fsync файла
        3. os.replace(tmp, target)   # атомарно на одном ФС
        4. fsync каталога

Читатель никогда не видит половину файла. При падении на шаге 3 старое состояние цело.

Блокировка записи

Один писатель — BFF. data/.lock с flock на время записи. Если лок занят — команда

отклоняется с busy, а не ждёт и не пишет поверх.

Процедура перехода на базу данных

Переход — не «поменять файлы на таблицы». Это отдельная работа с отдельным тестом.

Шаг 1 · Зафиксировать схему в базе

Таблицы отражают домен, а не JSON-документы. Ключевой момент — **не хранить целые

JSON-объекты в одной колонке**: тогда база превратится в файл внутри строки, и запросы

по полям останутся невозможными.

season            id, horizon_start, horizon_end, season_week_count, version
plan              id, season_id, status, goal_id, period_start, period_end, ...
phase             id, plan_id, objective, focus, load_range, ...
week              id, plan_id, season_week, start, end, status, focus, load_target, ...
request           id, week_id, sport, kind, focus, duration_min, ...
assignment        id, week_id, request_id, slot_id, start, duration_min, ...
workout           id, week_id, request_id, sport, kind, focus, status, actual_id, ...
step              id, workout_id, role, sport, target_type, target_value, ...
actual_session    id, season_id, date, sport, duration_min, distance_m, source, external_id, ...
week_summary      week_id, closed_at, totals, verdict, deviations, intensity, ...
command_log       id, type, issued_at, issued_by, result, ...
athlete           singleton row
methodology       model_id, kind, payload, version

Скрипт читает через порты (не напрямую по файлам), пишет через порты, сверяет количество

Шаг 5 · Переключить и оставить оба

Флаг в конфиге: storage.backend = files | sqlite. Оба адаптера живут в коде, пока

Один источник правды

  • Состояние — в хранилище, выбранном конфигом.
  • Производное (HTML-превью, снапшоты для клиента, отчёты) — пересчитывается, не хранится

вторым экземпляром. Кэш клиента — производная, помечена версией.

BFF03-BFF.md

Уровень: физический. Отвечает на вопрос «как приложение разговаривает с сервером».

BFF — тонкий слой. Доменной логики нет: маршруты, форматы, авторизация. Решения принимает

приложение (domain + services), BFF только переводит.

Технология

Python + FastAPI. Причина: вся логика планировщика уже на Python, домен переносится без

переписывания. BFF — тонкий слой поверх того же приложения, отдельный процесс только если

понадобится.

Маршруты

GET  /health                          liveness + версия
GET  /api/v1/snapshot                 весь сезон: план + состояние + version
GET  /api/v1/week/{n}                одна неделя
GET  /api/v1/actual/{n}              факт недели
GET  /api/v1/athlete                 профиль атлета
GET  /api/v1/season                  скелет сезона: фазы, недели, без деталей

POST /api/v1/commands                одна команда
POST /api/v1/commands/batch          несколько команд подряд (idempotency по id)
POST /api/v1/narrate                 спросить нарратора (текст, не числа)

GET  /api/v1/events                  SSE: изменения версии

Отдельного маршрута под загрузку факта нет: pull_fact — это команда, она идёт

POST /api/v1/commands как любая другая. Отдельный маршрут означал бы, что загрузка

факта — не действие пользователя, а фоновый процесс. Но по правилам модели загрузка

идёт по команде, и результат виден в diff.

Формат ответа

Успех:

{ "version": 42, "data": { ... } }

Ошибка:

{
  "version": 42,
  "error": { "code": "version_conflict", "message": "Состояние изменилось", "field": null },
  "data": { ...текущий снапшот... }
}

Коды: version_conflict · busy · not_found · invalid_command · invariant_violated ·

degraded · unauthorized.

Состояние ошибки — всегда с текущей версией, чтобы клиент мог показать «покажи заново»

без второго запроса.

Авторизация

В базе авторизации нет. Решение Кирилла (26.10.2026): аутентификацию и авторизацию

добавим позже.

Что это значит:

  • любой, кто достучился до адреса BFF в локальной сети, получает полный доступ;
  • в локальной сети это осознанный риск: по домашнему Wi-Fi может ходить кто угодно;
  • смягчение — BFF слушает 127.0.0.1 (тогда с телефона не достучиться) или доступ

ограничивается на уровне сети.

Когда появится внешний доступ, авторизация станет обязательной до него: иначе токен

или любые данные улетят открытым текстом через интернет.

Что оставляем на будущее: токен, HTTPS, роли. Место для них в коде — один модуль

app/api/auth.py; сейчас он пустой и ничего не проверяет.

  • Токен доступа в заголовке Authorization: Bearer <token>.

В базе заглушка не нужна — заголовка Authorization нет вовсе. Место для

будущей реализации: app/api/auth.py (сейчас не существует).

  • HTTPS обязателен, когда появится внешний доступ. Без TLS токен летает открытым

текстом. В базе (локальная сеть) HTTPS не нужен.

Один пользователь — один токен, без ролей, без refresh-механизма: ротация токена = команда

на сервере, устройства переавторизуются.

Кэш и версии

  • GET /snapshot — ETag = version. Клиент шлёт If-None-Match → 304 без тела.
  • На телефоне приложение должно открываться мгновенно и читать недель без сети —

поэтому клиент кэширует снапшот (см. 05-клиент.md).

  • Серверные кэши проекций: проекция считается из состояния и помечается версией;

при изменении состояния версия растёт, старые проекции вытесняются.

SSE вместо polling

GET /events — Server-Sent Events, отдаёт {version, changed[]} при изменении состояния.

Клиент перезапрашивает нужную проекцию. Проще и дешевле WebSocket для одностороннего

потока «сервер → клиент». Команды идут обычными POST.

SSE через прокси: отключить буферизацию (X-Accel-Buffering: no) и держать таймаут

прокси длиннее, чем heartbeat (heartbeat каждые 25 секунд).

Деградация

Что упало Что происходит
Garmin недоступен POST /actual/pull → degraded, план и чтение работают
Нарратор недоступен /narrate возвращает заглушку, остальное работает
Состояние нечитаемо сервер не стартует, /health → unhealthy, алерт

Внешний источник не роняет приложение — это правило деградации, а не пожелание.

Сетевой адрес

BFF слушает 0.0.0.0:8080 — доступен всем в локальной сети. Клиент ходит на

http://<ip-машины>:8080, адрес настраивается вручную и запоминается.

Внешний доступ отложен (см. 04-хостинг.md) — ни туннелей, ни проброса портов.

Нагрузка

Один пользователь, десятки запросов в день. Ресурсов хватает с запасом; оптимизации

(кэш, батчи, виртуализация) не нужны, пока не появятся реальные проблемы.

Структура процесса

coach-app/
  app/
    domain/       сущности, инварианты, производные — ноль I/O
    services/     сценарии: planner, goal_feasibility, week_builder, assessment
    ports/        контракты внешнего мира
    adapters/     реализации портов: storage, garmin, narrator, methodology
    api/          BFF: роуты, схемы ответов, auth
    main.py       сборка зависимостей, запуск
  migrations/
  tests/
  tools/

Зависимости строго вниз: api → services → ports → domain. adapters реализуют ports

и не импортируют api или services. domain не знает про формат хранения, HTTP и время.

Хранилище — за портами: BFF не знает, что это файлы или база (см. 02-хранилище.md).

Хостинг04-хостинг.md

Уровень: физический. Отвечает на вопрос «как приложение доступно с телефона».

В базе — только локальная сеть. Внешний доступ отложен (решение №1 в

08-развилки.md): ни домена, ни туннеля, ни проброса портов. Телефон подключается

к BFF по адресу машины в домашней сети.

Что это значит на практике

телефон (Wi-Fi дома) → http://192.168.178.43:8080 → BFF на hermeshome
  • BFF слушает 0.0.0.0:8080 — доступен всем в локальной сети, не только с самой машины.
  • Адрес машины в сети меняется при перезагрузке роутера (DHCP). Решение: имя хоста

hermeshome.local + fallback на текущий IP; в клиенте — поле адреса, запоминает

последний рабочий.

  • Вне домашней сети приложение недоступно. Это осознанно: база делается локальной,

внешний доступ — отдельная задача.

HTTPS: нужен для service worker

Service worker работает только на HTTPS или localhost. По обычному HTTP

с телефона браузер его не зарегистрирует — приложение откроется, но офлайн

не заработает: ни кэш оболочки, ни «страница открылась без сети».

Это ограничение браузера, а не выбор. Варианты:

Как Офлайн Заметки
HTTPS с самоподписанным сертификатом BFF за TLS на своём порту да Телефон спросит доверие один раз, предупреждение останется
localhost через туннель Туннель ведёт телефон на 127.0.0.1 да Service worker разрешён, но туннель — отдельная настройка
Обычный HTTP как сейчас нет Приложение работает, очередь команд в IndexedDB — тоже, но без service worker

Решение не принято. По умолчанию в базе — обычный HTTP: приложение доступно

и работает, офлайн включается отдельным шагом.

Доступ

В базе нет ни HTTPS, ни авторизации. Решение Кирилла (26.10.2026): аутентификацию

и авторизацию добавим позже.

Риск, который это создаёт: любой в домашнем Wi-Fi получает доступ к плану и факту.

Осознанно принят на старте. Смягчение, если понадобится: BFF слушает 127.0.0.1,

и тогда достучаться можно только с самой машины.

Когда появится внешний доступ, обязательными станут и HTTPS, и авторизация —

иначе данные и любой будущий токен улетят открытым текстом через интернет.

Раскладка карточки тренировки — как в эталоне: иконка вида спорта, название,

Метрики недели — три плитки: часы плана, число сессий, километры.

Офлайн

Что доступно без сети:

  • текущая неделя полностью;
  • соседние недели — сокращённо (дни и тренировки без шагов);
  • сезон — скелетом (фазы, недели, гонки);
  • профиль атлета.

Что требует сети: новые недели, вытягивание факта, связывание, закрытие недели.

Загрузка факта из Garmin в офлайне невозможна — команда ждёт в очереди.

Как показывается устаревшее: в шапке — «данные на <время>», кнопка «обновить».

Кэш хранит version состояния; сервер отвечает 304, если не менялось.

Размер офлайн-пакета: ориентир — до 1 МБ на текущую + соседние недели + сезон-скелет.

Команды в офлайне

Клиент не меняет состояние напрямую — только через команды. Команда, сделанная без сети,

уходит в outbox в IndexedDB и уходит на сервер при появлении сети.

outbox entry: {id, type, target, args, reason, created_at, attempts, last_error}
  • id генерируется на клиенте — по нему команда идемпотентна при ретраях.
  • Порядок сохраняется: команды одного типа зависимы, поэтому outbox — очередь, а не набор.
  • Пока команда в outbox, интерфейс показывает «в очереди», а не «сделано».
  • Конфликт версии → клиент показывает «состояние изменилось, посмотреть заново?» и

не применяет команду молча.

Текущая неделя

Номер текущей недели считает сервер: клиент спрашивает GET /api/v1/current-week

и берёт номер оттуда. В клиенте нет даты начала сезона — при смене горизонта

-season он не устареет молча.

Ручной выбор недели (для отладки и проверки) перекрывает серверный: номер

хранится в localStorage.

Адрес сервера

Приложение ходит на BFF по локальной сети: http://<ip-машины>:8080. Адрес

настраивается при первом запуске и запоминается. Внешний доступ отложен — пока

телефон должен быть в домашнем Wi-Fi.

Авторизация

Авторизации нет — добавим позже (решение Кирилла, 26.10.2026). Клиент не шлёт

Authorization и не спрашивает токен.

Место для этого заложено: api.js — единственное место, где ходят на сервер,

значит, добавление заголовка там не затронет остальной код.

События

Клиент подписан на SSE /api/v1/events. При сбое — backoff: 1с, 2с, 5с, 15с, 30с.

При обрыве — следующая синхронизация по обычному GET /snapshot.

Кэш в service worker

  • Оболочка (HTML, JS, CSS, иконки) — cache-first, обновление в фоне.
  • API — network-first; при отсутствии сети — из кэша с отметкой «устарело».
  • Никогда не кэшируются: ответы команд и ошибки.

Работа без сервера вообще

PWA ставится на экран телефона и открывается без сети — показывая кэш. Полноценная работа

невозможна (нет новых данных и нет применения команд), но приложение не выглядит сломанным.

Адаптеры06-адаптеры.md

Уровень: физический. Отвечает на вопрос «как подсистемы достают данные из внешнего мира».

Адаптер реализует порт. Логика знает только контракт порта и ничего не знает о том,

откуда пришли данные.

Garmin

Источник факта — только Garmin (подтверждённый инвариант I14). Второй источник активностей

в модели не подключён.

Что берём: activity_id · startTimeLocal · distance · duration · averageHR · maxHR ·

aerobicTrainingEffect · anaerobicTrainingEffect · vO2MaxValue.

Intensity minutes — по тренировке, не по дню. Garmin отдаёт:

  • get_intensity_minutes_data(cdate) — за день;
  • get_weekly_intensity_minutes(start, end) — агрегаты за период.

Недельные агрегаты Garmin считают пн→вс, неделя проекта — вс→сб. **Недельные агрегаты

не используем вообще**, считаем сами по тренировкам (I28).

Зоны Garmin ≠ зоны атлета. Garmin считает intensity minutes по своим зонам (~64 % и ~76 %

от HRmax). Зоны атлета важнее — считаем интенсивность сами по зонам атлета, шкалу источника

не храним. Если источник не делит интенсивность — всё идёт в moderate (I29).

Отсутствие данных — не ошибка. Нет тренировок — нет intensity minutes. Не заводим флаг

«неполная» (I27).

Виды спорта Garmin. activityType.typeKey — не имя тренировки, а тип:

running, cycling, indoor_cycling, lap_swimming, hiit, strength_training.

Имя при этом любое: ОФП Кирилл записывает как «High Intensity Interval Training».

Поэтому ОФП, силовая и HIIT — одна группа: в плане тренировка может быть помечена

любой из трёх, а в Garmin факт придёт как hiit или strength_training. Связать

их между собой можно, велосипед с бегом — нельзя.

Дубликаты: external_id = activity_id Garmin, уникален (I42). Повторная загрузка

того же id — обновление, не новая запись.

Деградация: Garmin недоступен → команда pull_fact отклоняется с degraded,

остальное приложение работает.

FIT-файлы. Garmin Connect отдаёт сводку по активности, но детальные метрики

(покадровые HR, каденс, дрейф, тренировочный эффект) живут в FIT-файле. pull_fact тянет

сводку; import_fit загружает сам файл и разбирает метрики из него.

Два пути получения активности:

  • pull_fact — команда: тянет из Garmin, создаёт ActualSession без плановой пары.

Дальше link_actual связывает её с тренировкой.

  • ручная запись — команда edit_actual: для силовых и ОФП, которых в Garmin нет.

Оба пути ведут в один и тот же факт. Разница только в source.

Stryd

Данные из Stryd не грузим. Сейчас берём то, что Stryd складывает в Garmin.

Отдельного адаптера Stryd нет и в базе не планируется — пока.

Нагрудный ремень при этом используется точно на важных тренировках — силовые интервалы,

пороговые сессии, тесты. Данные с ремня идут в Garmin, а оттуда в приложение: отдельный

канал не нужен. Отсюда следствие: в профиле атлета нет отдельного источника «Stryd» —

источник один, Garmin, а VDOT и зоны считаются по тому, что Garmin вернул.

Если позже понадобится тянуть данные Stryd напрямую (например, история GT по неделям,

которую Garmin не хранит), это будет отдельный адаптер — но решение не принято, и в базу

это не закладывается.

Что делать с VDOT: VDOT считается из гонки (результат на дистанции) и из тренировочных

темпов. Оба пути дают одно число — Athlete.vdot. Источник помечается, чтобы UI мог

показать диапазон, а не ложную точность.

Календарь

Взаимодействия с Google Calendar нет. Ни ICS, ни API календаря не подключаем.

Команда sync_calendar из контрактов удалена.

Доступность тренировок — это дефолтные слоты и инвентарь, которые лежат в логической

подсистеме «Среда» и версионируются как обычное состояние. Пример: бассейн доступен в пн/пт,

стадион — в пн, дорожка — вечером. Это данные, а не внешний источник: их можно менять

командами set_slots и override_slots, они попадают в версию состояния и в офлайн-кэш.

Что это значит на практике: если окно тренировки изменилось (бассейн закрыт на ремонт) —

это перекрытие слота командой, а не синхронизация с календарём.

Дэниэлс

Справочник соответствий VDOT ↔ темпы зон ↔ время на дистанции. Не внешний источник в смысле

сети — это версионируемые правила, которые приходят через MethodologyRepo.

Используется для: перевода цели в целевой VDOT (10К 40:00 → VDOT 52), темпов по зонам,

расчёта нагрузки.

Что забираем отдельно, позже: из Дэниэлса нужно будет достать **базовый план и типы

тренировок** — то есть рецепты занятий, из которых планировщик собирает неделю. В текущем

пайплайне это reference/daniels/daniels_tables.json (56 строк темпов, 44 строки времён)

и state/workout_templates.json (10 типов тренировок: vo2max, threshold_speed,

threshold_power, tempo, mixed, pyramid, …).

Это отдельная работа: разобрать таблицы и привести к доменным правилам. В базу входит

как отдельный этап — пока типы тренировок живут в пайплайне и берутся оттуда.

Нарратор (LLM)

Не считает и не применяет. Формулирует: объяснение плана, варианты решения, текст

для пользователя.

Контракт: один вызов через порт, ответ валидируется по схеме, промпты — в коде или данных.

Нет ключа → детерминированная заглушка, приложение работает.

Правило роста формы

Отдельный адаптер, но по сути — часть правил методологии (MethodologyRepo).

Правило отвечает на вопрос: сколько VDOT атлет может набрать к дате цели при текущем

объёме и возрасте.

На старте — заглушка. Пока правило не задано, вердикт по достижимости честно отвечает

«не могу оценить» и предлагает следующий шаг. Заглушка ставится явно, с пометкой, что

правило не написано: выдуманное число опаснее отсутствующего.

Спорт и общие правила для всех адаптеров

  1. Каждый внешний вызов — с таймаутом и политикой retry.
  2. Ошибка внешнего источника никогда не роняет приложение: деградация вместо отказа.
  3. Любое число из источника хранится с source и external_id.
  4. Секреты — в конфигурации приложения, не в репозитории и не в хранилище.
  5. Адаптер не импортирует api и services — только domain и ports.

1 · Хостинг — отложен, в базе только локальная сеть

Решено: внешний доступ не делаем. Приложение доступно по локальной сети —

домашний Wi-Fi, телефон в той же сети подключается к BFF по адресу машины.

  • Домен, HTTPS, Cloudflare Tunnel, Tailscale — всё отложено.
  • В базе: BFF слушает локальный адрес, клиент ходит на http://<ip>:8080.
  • Снаружи наружу ничего не смотрит: туннелей, проброса портов, публичных адресов.

Что это меняет: HTTPS не обязателен в базе — но токен всё равно проверяется, иначе

любой в сети заходит. Когда появится внешний доступ, HTTPS станет обязательным.

Когда вернуться к вопросу: когда понадобится доступ извне дома — тогда выбираем

вариант из 04-хостинг.md (A · Cloudflare Tunnel рекомендован как основной).

2 · Формат хранения — не развилка

Формат меняется по триггерам, не по решению. Путь зафиксирован в 02-хранилище.md:

сначала файлы, при срабатывании триггера — SQLite, переход через порты, контрактные

тесты на оба адаптера.

Триггеры: второй писатель · запросы по произвольным полям · состояние не влезает

в память · нужна транзакция между сущностями. Пока ни один не сработал — файлы.

3 · План и факт — стартуем с импортом

Решено: A · импорт. Сезон 2026–27 уже наполнен — импорт даёт рабочее состояние сразу

и обкатывает домен на реальных данных.

Что не переносится автоматически — перечислено в 02-хранилище.md: связь план↔факт,

summary, недельные макро-цели.

4 · Методология — движок внутри Планирования

Решено: A. Методология — данные, а код чтения правил живёт в планировщике.

Новая методика всегда требует кода. Отдельного слоя «правила + исполнитель» нет.

Простота важнее гибкости: пока это работает, менять нечего.

5 · Достижимость — функция методологии

Решено: функция методологии. Отдельной подсистемы «Цель и достижимость» больше нет —

в логической модели 7 подсистем, а не 8.

Как устроено: правило роста формы живёт в методологии, вердикт считает планировщик

(шаг 1). Пока правило не написано, вердикт честно отвечает «не могу оценить».

6 · Потолок формы — из методологии, сначала заглушка

Решено: A · из правил методологии. Правило роста — часть знаний планировщика.

Но по факту в начале — заглушка. Пока правило пустое, шаг 1 отвечает «не могу оценить»

и предлагает следующий шаг, а не выдумывает число. Заглушка ставится явно, с пометкой,

что правило не задано.

Внешнего источника прогноза не будет. Когда правило появится — оно станет частью

методологии, а вердикт будет ссылаться на конкретное правило.

7 · Факт и Оценка — две подсистемы

Решено: A. Факт принимает и нормализует, Оценка связывает с планом и считает итог.

Граница с внешними источниками остаётся чёткой: приём Garmin — адаптер, а не часть

логики.

8 · Нарратор — нужен, с заглушкой

Решено: A. Порт NarratorPort есть с первого дня, ключа может не быть.

Нет ключа → детерминированная заглушка, приложение работает.

9 · Батч-рендеры пайплайна — оставляем параллельно

Решено: A. ~/coach продолжает рендерить HTML-превью недель и макро-обзор как есть.

Приложение делает свои проекции.

Перенос 82 КБ render_html.py — не в базу. Отдельная задача, когда понадобится.

10 · Правила из Дэниэлса — отдельной задачей после этапа 3

Решено: A. Этап 3б в 07-реализация.md.

Планировщик строится на текущих шаблонах пайплайна, разбор Дэниэлса идёт параллельно

и подключается, когда готов.

Что осталось открытым

  • Правило роста формы — какое считаем рабочим. Заглушка на старте, но без решения

задача «скажи, если цель недостижима» не выполняется по-настоящему.

  • Внешний доступ — когда понадобится. Тогда вернёмся к 04-хостинг.md.
  • Настоящая аутентификация — отложена, токен-проверка закрывает базу.

Блокером для начала реализации считаю только правило роста формы: без него шаг 1 —

заглушка, но это не мешает строить остальное.
