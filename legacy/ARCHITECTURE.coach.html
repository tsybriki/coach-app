TL;DR — что это и зачем

  1. Один JSON-файл правды на каждый срез (athlete / season_plan с goals[] и phases_for_goals / constraints / progress / overrides / fit_store).
  2. Вся арифметика идёт в Python (lib/). Модель вызывается через одну обёртку ask_model.py с JSON-schema. Skill'ы не пишут промпты руками.
  3. 4 точки расширения: metrics/, season_replan, plan_generate (с constraints + volume_progression + goal_allocator), analyze (4 режима).
  4. Несколько целей в одном сезоне: goals[] (например spring 10K + autumn Olympic triathlon). plan_generate распределяет объём через goal_allocator.py — оптимум с учётом adaptation_rates, trade-off'ы показывает явно, решение за Кириллом.
  5. control_points живут в season_plan с привязкой goal_id; общие (discipline-agnostic) — без goal_id.
  6. constraints — рамка. plan_generate читает, coach-plan-adjust правит (с подтверждением).
  7. FIT retention = 14 дней → удалить.
  8. Все спортивные skill'ы названы по схеме 'coach-<area>-<verb>'.
  9. Каждое решение моделью логируется в decisions/. Retention-проход логирует, что удалено.
  10. Вес: weight_history[] в athlete.json + авто-синк из Garmin через cron + одна строка в weekly_report + ручная правка через coach-plan-adjust. Без целевого веса, без BMI/калорий, без алертов. Минимум.

Множественные цели — как устроено

Один season_plan с goals[]. phase принадлежит goal. goal_allocator распределяет часы/нед между целями с учётом adaptation_rates.

~/.hermes/coach/state/season_plan.json

goals[]
цели сезона: [{id, discipline:'run_10k'|'tri_olympic'|..., race_date, goal_metric:{type,target}, priority:1..n, primary:true|false, notes}].
phases[]
теперь с goal_id. Каждая фаза принадлежит одной цели. Пример: [run_base, run_build, run_specific, run_taper, race_1, transition, tri_base, tri_build, tri_specific, tri_taper, race_2].
adaptation_rates[]
per-discipline коэффициенты восприимчивости к нагрузке: {run:1.0, swim:0.55, bike:0.7, strength:1.5}. ЧСС-час бега ≠ ЧСС-час велосипеда. Используется goal_allocator для распределения часов между целями.
control_points[]
теперь с goal_id для целевых TT и без goal_id для общих метрик (HR drift, cadence).
races[]
сохраняется как список гонок (по одной на goal с race_date).
transition_phases
фаза перехода между целями (run taper → tri base). Снижение объёма одной дисциплины + вход в другую.

Правило: goals задаёт coach-plan-season при создании сезона на основе интервью. Изменение goals = season_replan с reason='add_goal' / 'swap_goal' / 'drop_goal'.

Вес — минимум без переусложнения

Просто следим. Без целей, без BMI, без алертов.

~/.hermes/coach/state/athlete.json (поле) + lib/garmin_weight.py

athlete.weight_kg_current
последний известный вес, обновляется при любом новом измерении.
athlete.weight_history[]
[{date, kg, source:'garmin'|'manual'}] — append-only. Без лимита на размер (одна запись в день максимум = ~100 записей/год).
lib/garmin_weight.py
читает последний вес из Garmin (garth или garminconnect). Вызывается из cron eae7b0d88b4a (ежедневно 02:00). Если новых данных нет — no-op.
weekly_report.weight_line
одна строка в сводке недели: «Вес: 101.7 кг (Δ −0.3 за 7д, тренд ↓)».
coach-fit-review (опц.)
при coaching/lookback и ≥ 4 нед истории weight_history — показывает рядом с метриками тренд веса за период. Без валидации, без cited_principle для самого веса.
coach-plan-adjust (ручная)
по команде «я взвесился — 95.8» пишет в weight_history с source='manual', обновляет weight_kg_current.

Правило: НЕТ: target_weight, BMI, калорий, алертов на дельту. ЕСТЬ: текущий вес + история + строка в weekly_report. Всё остальное — потом, если понадобится.

goal_allocator.py — как распределяется объём

  1. 1
    Вход
    goals[], phases_for_each_goal с hours_per_week_target, constraints.weekly_windows, adaptation_rates.
  2. 2
    Нормализация
    Перевод raw hours → effective_cost hours через adaptation_rates (ЧСС-час бега = 1.0, вел = 0.7, плав = 0.55). Это «истинная» стоимость тренировки для организма.
  3. 3
    Балансировка
    Подбираем долю effective_cost часов каждой цели так, чтобы не превышать constraints.max_total_effective_cost_per_week. Первая цель (primary) получает baseline, остальные делят остаток.
  4. 4
    Candidates
    goal_allocator возвращает 2-3 варианта распределения: 'primary-приоритет', 'баланс 60/40', 'баланс 50/50'. Для каждого: что выигрывает, что проигрывает, на сколько часов.
  5. 5
    Trade-off показ
    Кирилл видит: «вариант A: 10К получает 5.5ч, triathlon получает 4.5ч (риск: triathlon run-leg просядет на 5-8 сек/км). Вариант B: 10К 4.5ч, triathlon 5.5ч (риск: 10К медленнее на 10-15 сек/км)».
  6. 6
    Решение
    Кирилл выбирает. coach-plan-season фиксирует: chosen_allocation + reason (чтобы потом, при replan, было видно, чем он руководствовался).
  7. 7
    plan_generate применяет
    phases[] в season_plan.json обновляются hours_per_week_target в соответствии с chosen_allocation. Дальше — обычная сборка W_N.

Ключ к предсказуемости: goal_allocator НЕ выбирает за Кирилла. Он даёт 2-3 варианта с явным trade-off'ом. Решение — человек. Это про оптимум-как-подсказка, а не оптимум-как-default.

season_plan.json — структура (v9, с goals[])

  1. goals[]: [{id, discipline, race_date, goal_metric, priority, primary}] — цели сезона.
  2. phases[]: [{id, goal_id, start, end, hours_per_week_target?}] — каждая фаза принадлежит goal (или null для общих).
  3. transition_phases: явный тип для перехода между goal.
  4. control_points[]: [{id, goal_id|null, date, what, metric_target, measures, protocol?}].
  5. races[]: [{goal_id, date, name, start_time}].
  6. chosen_allocation: {strategy, g_xxx_eff_pct, reason, snapshot_date} — зафиксированное решение Кирилла.
  7. adaptation_rates[]: per-discipline коэффициенты (используются goal_allocator).
  8. fit_ingest матчит FIT-дату с CP и пишет actual_metrics в season_progress.control_points[id].

volume_progression + goal_allocator — поведение plan_generate

  1. 1
    Вход сезона
    season_plan.json → goals[], phases[] с goal_id, hours_per_week_target.
  2. 2
    Вход constraints
    weekly_windows, preferred_slots, forbidden.
  3. 3
    Normalize
    goal_allocator переводит raw hours → effective_cost hours через adaptation_rates.
  4. 4
    Candidates
    goal_allocator возвращает 2-3 варианта распределения (primary-приоритет / 60-40 / 50-50) с явным trade-off.
  5. 5
    Кирилл решает
    Применяется chosen_allocation. phases[].hours_per_week_target обновляется.
  6. 6
    volume_check
    STOP + diff + согласование при gap.
  7. 7
    Раскладка
    plan_generate раскладывает по weekly_windows с preferred_slots + запреты.
  8. 8
    Прогрессия
    Каждая W_N получает hours_target с учётом volume_progression_rules.

Ключ к предсказуемости: Цели делят объём через goal_allocator. Объём — сезонный параметр. plan_generate НЕ фантазирует.

Точка расширения 3 · W_N: season_plan + constraints + overrides + inline Zwift

  1. 1
    Вход сезона
    season_plan.json → phase (goal_id), hours_target, CP_in_range, focus (например 'long Z2' / 'threshold intervals' / 'bike endurance').
  2. 2
    Вход формы
    athlete.json + weekly_report (как прошла ПРЕДЫДУЩАЯ неделя) → fatigue_score, recovery_hr_drop.
  3. 3
    Вход constraints
    constraints.json → weekly_windows, preferred_slots, forbidden, auto_zwift (правила для inline Zwift).
  4. 4
    Размещение slot-ов
    plan_generate раскладывает focus-недели по weekly_windows + preferred_slots. Каждый slot имеет: kind, duration_min, day, time, location, focus_tags.
  5. 5
    Inline Zwift check
    Для каждого bike/brick-слота plan_generate проверяет constraints.auto_zwift: {duration_min_max:90, location:'home_stationary_bike', kind:['bike','brick'], focus_must_have:['Z2','Z3','intervals']}. Если совпало → авто-дёргает coach-plan-zwift inline. Иначе → slot без workout_ref.
  6. 6
    Inline Zwift candidates
    coach-plan-zwift.search(criteria из slot.focus_tags + duration_min) → candidates[] (2-4). plan_generate пакетно собирает все bike-слоты требующие Zwift, рендерит ОДИН HTML с cards всех slot-ов.
  7. 7
    Решение Кирилла
    Кирилл голосует по каждому slot (или 'skip — оставить пустым'). Решения в decisions/<date>-<slot>-zwift.json. Если 'skip' — slot остаётся без workout_ref, Кирилл сам выберет workout позже (или сделает на улице).
  8. 8
    workout_ref в slot
    Для каждого выбранного candidate: zwift_sync → Garmin Connect → workout_ref = {url, garmin_workout_id, scheduled_date} записывается в plan-wN.json в соответствующий slot.
  9. 9
    Overrides merge
    merge overrides + проверка конфликтов с focus, CP-датами и forbidden. Slot с workout_ref защищён от override (Кирилл должен явно 'отвязать workout').
  10. 10
    Выход
    plan-wN.json со всеми slots (часть с workout_ref, часть без) + decisions/audit + render_html.py → wN-mobile.html. Один артефакт, всё сразу.

Ключ к предсказуемости: ОДИН этап планирования. plan_generate раскладывает focus по окнам + INLINE дёргает coach-plan-zwift для bike/brick-слот-ов удовлетворяющих constraints.auto_zwift. Кирилл получает готовый план с workout_ref-ами, без отдельного шага 'искать Zwift'. Если Кирилл хочет перевыбрать workout — команда 'переподбери slot X', plan_generate передаёт в coach-plan-zwift заново. Это НЕ разорванный двухшаговый процесс.

  5. 5

  6. 6

  7. 7

Pre-amble: Pre-amble наследуется всеми: «Ты строго в рамках athlete.json + season_plan.json + constraints.json + вывод указанной функции. Любой факт вне — откажись. В coach-fit-review/coach-fit-trend каждое утверждение требует cited_principle.»

Правило: area ∈ {plan, fit}, verb ∈ {week, season, adjust, ingest, review, trend, onboarding}. coach-plan-adjust — единственный, кто правит constraints (с подтверждением). coach-plan-season — единственный, кто вызывает goal_allocator. coach-plan-zwift — единственный, кто обращается к WhatsOnZwift.

Scoreboard-флоу — каждый запрос проходит одну лестницу

  1. 1
    Hook
    load_athlete_context: athlete + season_plan (goals, phases_for_goals, chosen_allocation) + constraints + last override + last decisions.
  2. 2
    Skill-route
    По смыслу → 1 из 7 coach-* skill'ов. Скилл НЕ пишет промпт.
  3. 3
    Загрузка?
    «загрузи FIT» → fit_ingest.py → fit_store/ + (если CP-дата) actual_metrics.
  4. 4
    Данные + метрики
    Python lib. W_N: goal_allocator (если ещё не выбран) + volume_check + constraints + CP-слоты. Analyze: tier по доступности + goal_id-фильтр.
  5. 5
    Allocation?
    «как распределить объём между целями» → goal_allocator.py → candidates[] с trade-off → Кирилл выбирает → chosen_allocation в season_plan.
  6. 6
    Inline Zwift для bike-слотов
    plan_generate проверяет constraints.auto_zwift. Для каждого bike/brick-слота удовлетворяющего правилу (≤90 min, home_stationary_bike, focus) — дёргает coach-plan-zwift inline, собирает candidates, Кирилл голосует голосом, zwift_sync пишет workout_ref в plan-wN.json. Один шаг, не два.
  7. 7
    Retention?
    cron (еженедельно) → fit_retention.py → удалить FIT > 14 дней.
  8. 8
    Replan?
    «перепланируй сезон» → season_replan.py → новый season_plan.json + constraints check + allocation check + archive старого.
  9. 9
    Модель
    ask_model.py с JSON-schema. coach-fit-review/coach-fit-trend → обязателен cited_principle.
  10. 10
    Audit + выход
    decisions/<date>-<slot>-{analyze,w,replan,retention,allocation}.json. Render: JSON + self-contained HTML.

Ключ к предсказуемости: Всё, что считается — Python. Интерпретации — ask_model + JSON-schema + cited_principle. Несколько целей: распределение через goal_allocator (candidates, не default). control_points в season_plan. constraints = рамка. FIT retention = 14 дней.
