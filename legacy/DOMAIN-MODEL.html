01 Слои и правило зависимостей

Мозг — это не «сервис с ИИ». Это чистый код с четырьмя слоями, где зависимости идут строго вниз. Мозг не знает, где лежат файлы, что такое HTTP и что такое Garmin.

domain   Session · Step · Week · SeasonPlan · Preferences · Athlete · Actual
         — чистые данные и правила над ними. Ноль I/O.

services Planner · WeekBuilder · StepBuilder · Allocator
         Replanner · Adjuster · GateEvaluator · Metrics
         — сценарии: связывают домен и порты.

ports    PlanRepo · ActualRepo · AthleteRepo · CalendarPort
         ActivityPort · ProgressPort · LLM · Clock
         — контракты. Форма данных и поведение при сбое зафиксированы ДО кода.

adapters JsonPlanRepo · GarminActivityAdapter · StrydProgressAdapter
         LlmNarrator · SystemClock
         — знают про файлы, сеть, форматы.
Правило одного источника правды Всё состояние — в state/*.json (~/coach). Клиент (телефон) — кэш снапшота, а не второй источник. Поэтому «правка в телефоне» = команда в outbox → сервер/мозг → снапшот.
02 Step — ядро гибкости

Тренировка не должна храниться строкой. Единица смысла — шаг. Шаг отвечает на три независимых вопроса, и в текущих данных они смешаны в один плоский словарь:

ВопросПолеЗначения
Что измеряем — объёмdimensiontime · distance · reps · effort_only
В чём задаём интенсивностьtargethr (зона) · pace · rpe · power · none
Как устроена структураstructureflat (шаги подряд) · sets (повторы с отдыхом)
Поправка к твоей формулировке «Пульсовая зона / время / скорость / отрезок» — это не четыре вида шага. Это два разных измерения: объём (время/дистанция) и интенсивность (HR/темп/RPE). А «отрезок» — это не basis, а структура (повторы с отдыхом). Если смешать их в одно поле basis, получится неразличимое «distance+hr» против «time+hr» и любая валидация станет guess'ом.
Step union
Обязательные: phase, dimension, target, duration_min. Опционально: distance_m, reps, notes.
phaseenum
warmup · work · recovery · cooldown · rest · set · transition · main
dimensionenum
time · distance · reps · effort_only. Что мерим.
targetobject
discriminated union: {type:'hr', zone:'Z5', bpm:164} · {type:'pace', from:'4:15', to:'3:50'} · {type:'rpe', rpe:8} · {type:'none'}
duration_minint
длительность шага. Всегда считается — даже когда задан отрезок (для плана по времени).
distance_mint?
для dimension=distance. 800 / 200 / 250 (отдых) / 3000.
repsint?
для dimension=reps — 3×45с планка, 2×12/стор.
notesstring?
пояснение для человека, не для логики.

Шаг-повтор (set)

Отрезок — это структура: список рабочих шагов и шагов отдыха. В текущих данных это set_repeats внутри шага с phase='set'.

Step {
  phase: 'set'
  dimension: 'distance'
  label: '3×800 с прогрессией 4:15 → 3:50'
  reps: 3
  set_repeats: [
    { phase:'work',     dimension:'distance', distance_m:800, target:{type:'pace', from:'4:15'} },
    { phase:'recovery', dimension:'distance', distance_m:250, target:{type:'hr', zone:'Z1', bpm:115} }
  ]
}
time + hr time + pace distance + pace distance + hr reps sets без интенсивности

Инварианты Step

  • duration_min > 0 у каждого шага; сумма шагов = duration_min сессии.
  • Зона HR принадлежит Athlete.hr_zones — step не хранит свои границы зон, только zone и (опционально) bpm.
  • Темп хранится строкой M:SS на км; если VDOT изменился — темпы пересчитываются, а не хранятся навсегда.
  • Шаг без интенсивности (target.type='none') — разминка/заминка/мобилити.
  • В структуре sets чередование work/recovery обязательно и нечётное число рабочих шагов.

Два вида сессий — разделить явно

Сейчас в slots смешаны тренировки и силовые/мобилити-блоки. У них разная природа: у силовых нет темпа и пульсовой зоны, у беговых — нет упражнений.

ТипШагиПример
Cardioвремя/дистанция + targetЛёгкая пятёрка — Z1 30мин
Qualitysets с прогрессией3×800 прогрессия + 4×200
Strengthупражнения: {name, reps, rest}Core circuit ×2: планка, bird-dog…
Mobilityодно упражнение + времяhip openers, glute bridge
Что это даёт UI умеет рендерить четыре разных карточки сессии вместо одной «как получится». Плюс разные чек-листы выполнения, разная логика «выполнено» и разные правила для Replanner (силовой блок можно перенести, 90-минутный лонг — нельзя без потери).

Это то, что ты назвал «дефолтный пользовательский календарь недель» + «доступность оборудования». Сейчас это state/constraints.json, и я бы не называл это preferences — это ограничения. Разделить на два типа объектов.

В UI это два разных экрана с разной степенью жёсткости, и пересечение с сезонными правилами должно быть видно до применения, а не после.

09 Метрика прогресса

Ты назвал VDOT — и это правильный выбор: он переводит форму в одно число, которое можно поставить рядом с целью (46.4 сейчас → 52 цель) и которое не зависит от того, какой тренировкой ты это набрал.

ProgressMetric value object
vdotnumber
текущий (48 заявлен, 46.4 по факту 10К 44:06) и целевой (52).
trendenum
improving · stable · plateau · declining · recovering_after_injury
race_pace_equivalentstring
«4:24/км» — текущий темп, эквивалентный текущему VDOT.
gap_to_goalobject
{sec_per_km: 24, pct: 10.3} — расстояние до цели в тех же единицах, что и цель.
sampleslist
история: {date, vdot, source, confidence}. Confidence обязателен: VDOT из разовой 10К ≠ VDOT из серии за 6 недель.
Второй источник — обязателен VDOT из Stryd (GT/VO2) и VDOT из таблицы Дэниэлса по результату 10К — это разные вещи. Хранить оба, помечать источник, и в UI показывать диапазон «46.4–48», а не ложную точность. Когда расходятся — это сигнал, а не повод выбрать «правильное».
10 Команды над планом

«Неделя = выходная», «неделя = сниженный объём», «перенести неделю», «запросить корректировку» — это не правки файлов, а команды. Мозг принимает команду, пересобирает, отдаёт diff. UI показывает diff до применения.

для идемпотентности (повтор из outbox не должен примениться дважды).
typeenum
см. список ниже.
argsobject
параметры команды.
reasonstring
обязательно. Команда без причины — не команда, а каприз.
issued_at · issued_byts · enum

Ответ мозга на команду

{
  command_id: 'c-8f2a',
  status: 'proposed',        // proposed | applied | rejected
  diff: [
    { scope:'week', target:'W3', change:'mode', from:'normal', to:'deload' },
    { scope:'week', target:'W3', change:'slots', removed:['ср-long_run'] },
    { scope:'week', target:'W4', change:'load', from:7.3, to:6.9 },
    { scope:'season', target:'W4..W49', change:'phase_shift', weeks:+1 }
  ],
  consequences: [
    'Объём W3: 6.5 → 5.2 ч (−20%), в коридоре фазы [4.96, 9.74]',
    'Длинный Z2 90мин смещён на W4 — прогресс к фазе run_build не пострадает',
    'Сдвиг фазы не требуется: цель 18.04 сохраняется'
  ],
  warnings: [ 'Потеря 1.4 ч объёма за неделю — компенсируется деload-неделей W12' ],
  requires_confirmation: true
}
Три уровня последствий local — меняется только эта неделя, применяется сразу. ripple — меняются следующие N недель, показывается diff и ждёт подтверждения. season — меняется цель/фазы/гоночный календарь, всегда ждёт подтверждения и всегда показывает цену (сдвиг даты, потеря объёма, риск для цели).
Про «перенос недели» — ключевой вопрос Если неделю сдвигают, объём не исчезает. Варианты: (а) потеря — неделя вычитается из общего объёма, и если горизонт не резиновый, цель под угрозой; (b) сдвиг фазы — объём сохраняется, но всё смещается, гонка может стать недостижимой. Правильный ответ зависит от того, где в сезоне стоит неделя. Мозг должен выбирать сам и объяснять, а не спрашивать «как хочешь».

12 Проекции для UI

UI не знает доменную модель. Он получает готовые проекции — и это позволяет держать клиент тонким, а офлайн-кэш — предсказуемым.

ЭкранПроекцияРазмер
НеделяWeekListView — сессии по дням, статусы, объём, кнопка «запросить корректировку»~8 КБ
СессияSessionDetailView — шаги с целями, «почему», гараж-редактор~4 КБ
СезонSeasonView — 49 недель, полоса фаз, отметки CP и гонок, «где я»~15 КБ
План vs фактComparisonView — дельта по метрикам + по сессиям~6 КБ
КомандаCommandProposalView — diff, последствия, предупреждения, кнопки «применить/отклонить»~3 КБ
Офлайн-пакет На старте клиент тянет: текущую неделю (полная), ±1 неделю (сокращённая), сезон (скелет без недельных деталей), athlete/constraints. Итого ~40 КБ — помещается в кэш и обновляется быстро. Полные детали соседних недель — по запросу, с кэшированием.

Кэш и outbox

  • IndexedDB (не localStorage — там строковые лимиты и синхронный API): снапшот + метаданные свежести.
  • Outbox: очередь команд с идентификаторами; при появлении сети — push, при конфликте — сервер возвращает текущее состояние, клиент переспрашивает пользователя.
  • Service worker: отдаёт кэш мгновенно; помечает «показано устаревшее, обновляю…».
  • Конфликт правок: план — источник правды на сервере; клиент не пишет в план напрямую, только через команды.

14 Что нужно решить

Три развилки меняют модель, а не детали реализации. Остальное — работа.

A Где живёт сервер
Вариант 1 — сервер на этой машине + доступ по сети: полноценные команды с телефона, но нужен доступ извне (туннель/домен). Вариант 2 — PWA без сервера: чтение офлайн бесплатно, но «запросить корректировку» и правки работают только дома, синхронизация — экспорт/импорт JSON. Вариант 3 — гибрид: сервер только для команд, чтение — полностью офлайн.
B Цена переноса недели
Потеря объёма или сдвиг фазы — и что показывать: «цель под угрозой» или «сдвигаем дату».
C Граница полномочий LLM
Моё предложение: LLM формулирует и объясняет, домен считает и применяет, результат всегда показывается как diff до применения, а LLM-ответы хранятся как текст рядом с решением (не как основание).
Порядок, который я предлагаю 1. Закрыть §13 дыры 1–5 в домене (миграция данных, без этого UI будет угадывать).
2. Написать контракты портов + типы (§2, §11) как схему — до реализации.
3. Собрать Read-путь: сезон → неделя → сессия → факт. Это то, что нужно для первого офлайн-клиента.
4. Write-путь: команды → Replanner → diff → применение.
5. Приложение: PWA-клиент, офлайн-кэш, outbox.
