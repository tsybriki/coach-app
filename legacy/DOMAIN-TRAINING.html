00 Как связаны уровни

Четыре сущности. Каждая отвечает на свой вопрос, и между ними есть только два направления связи: сверху вниз (цель порождает тренировку) и снизу вверх (выполненная тренировка корректирует цель).

Goal — зачем
Измеримая цель: 10К за 40:00, 18.04.2027. VDOT 46.4 сейчас → 52 цель.
порождает фазы, объём, структуру
Plan — что и когда
Сезон (49 недель, фазы, макро) и неделя (сессии по дням). Цель раскладывается в скелет.
наполняется сессиями по календарю
Session — одна тренировка
«Качественная: VO2max», 51 мин, стадион. Дисциплина, subkind, цель, логика, шаги.
собирается из шагов
Step — мельчайшее действие
15 мин Z1 разминка · 800 м @ 4:15 Z5 · 250 м Z1 отдых. Объём + интенсивность.
Направления связи Вниз: Goal → Phase → Macro(неделя) → Session → Step. Каждый уровень добавляет детализацию, ничего не выбрасывая.
Вверх: Actual (факт) → Session выполнена → неделя → прогресс (VDOT) → «достижима ли цель». Факт — единственный источник, который двигает Goal.
Что это даёт мозгу Одно место отвечает за «правильно ли это построено»: Step — нижний уровень, где нет никакой предметной логики, только объём, интенсивность и структура. Всё, что предметное (темп 4:15, зона Z5, объём 3200 м), живёт на верхних уровнях и попадает вниз через конкретные поля. Поэтому «заменить структуру тренировки» = заменить список шагов, не трогая цель, фазу и календарь.

Производные от цели

Цель — единственное место, где задаются числа верхнего уровня. Всё остальное выводится и может быть переопределено только с причиной.

Цена VDOT Темпы в шагах сейчас захардкожены как строки («4:15», «5:35»). При смене VDOT они устаревают и никто об этом не узнает. В домене темп должен вычисляться из профиля, а в Step храниться как {type:'pace', from, to} + pace_basis_vdot — тогда «VDOT вырос» автоматически меняет все темпы, а старая строка не может выжить незаметно.
02 Plan

План двухуровневый: сезон задаёт скелет на 49 недель, неделя — это конкретные тренировки по дням. Связь между ними: макро недели говорит, что должно быть, а календарь и предпочтения — где именно это стоит.

Как макро превращается в неделю

Это ядро планировщика, и оно объясняет, почему в данных так много разных полей.

Macro недели W3:
  run_km: 35   long_km: 14   quality: {goal:'vo2max', scale:'medium', variant_id:'3x800prog+4x200', work_m:3200}
  core: '2×25м'   bike: '1×60м'   swim: '1×30м'   total_h: 6.24

         ↓  CalendarPort + WeeklyPreferences + Constraints
         ↓  (что доступно, когда, каким ресурсом)

Неделя W3:
  ВС 12:00  run/easy        30мин  Z1
  ПН 06:30  strength/core   25мин
  ПН 18:45  run/quality     51мин  ← из quality: vo2max + medium + variant
  ВТ 07:00  run/easy        30мин  Z2
  ВТ 18:30  run/easy        40мин  Z2   ← добор km до 35
  СР 17:00  run/long_z2     90мин  14К
  ЧТ 19:00  bike/stationary 45мин
  ПТ 20:00  swim/easy       45мин
  СБ 09:00  strength/core   35мин  ← core + mobility
Три слоя ограничений на неделю 1. Macro говорит, что должно быть (35 км бега, одна качественная, силовая, вел, плавание).
2. Календарь и preferences говорят, когда это может стоять (пн 18:45, ср 17:00) и чем (бассейн доступен пн и пт — значит плавание в пятницу, не в среду).
3. Constraints говорят, что запрещено (ср вечер — интенсивных нельзя; ≤ 11 ч в неделю).
Если слои противоречат друг другу — приоритет: Constraints > Preferences > Macro. Macro — мягкий: он говорит «нужно», но может быть урезан.

Три вида сессий

Сейчас силовые и кардио лежат в одной структуре, хотя это разные вещи: у силовой нет темпа и пульсовой зоны, у кардио нет упражнений.

ВидШаги устроены какПример
Cardioобъём (время/дистанция) + интенсивность (HR/темп)Лёгкая пятёрка — Z1 30мин
Qualityнаборы с прогрессией: работа + отдых3×800 прогрессия + 4×200
Strengthупражнения: {name, reps, rest}Core circuit ×2: планка, bird-dog…
Зачем разделять Разные карточки в UI (у силовой — список упражнений, у качественной — интервальная сетка). Разные правила для Replanner: силовой блок можно перенести на другой день без потерь, 90-минутный лонг — нельзя, это ключ фазы. Разные чек-листы выполнения.

subkind — это не ярлык, а рецепт

subkind определяет, по какому шаблону собираются шаги. Это то, что позволяет генерировать тренировки, а не хранить их: easy → разминка Z1 + Z2 + заминка; long_z2 → то же, но 90 мин; quality → структура из макро (variant).

easy long_z2 quality tempo intervals recovery stationary_z2 core tt
04 Step

Шаг — единственное место в домене, где нет предметной логики. Только три вещи: что делаем (объём), с какой интенсивностью (цель), как устроена структура.

Поправка к исходной формулировке «Пульсовая зона / время / скорость / отрезок» — это не четыре вида шага. Это два независимых измерения плюс структура:
· объём — time · distance · reps
· интенсивность — hr · pace · rpe · none
· структура — flat (шаги подряд) · sets (повторы с отдыхом)
«Отрезок» — это структура, а не способ задания интенсивности. В одном поле basis варианты «distance+hr» и «time+hr» становятся неразличимы, и любая валидация превращается в угадывание.
Step union
Обязательно: phase, dimension, target, duration_min. Опционально: distance_m, reps, label, notes.
phaseenum
warmup · work · recovery · cooldown · rest · set · transition · main
dimensionenum
time · distance · reps. Что мерим.
targetunion
{type:'hr', zone:'Z5', bpm:164} · {type:'pace', from:'4:15', to:'3:50'} · {type:'rpe', rpe:8} · {type:'none'} — в чём задаём интенсивность
duration_minint
длительность. Всегда считается — даже для отрезков, чтобы план был в часах.
distance_mint?
800 · 250 (отдых) · 200 · 3000
repsint?
3×45с планка · 2×12/стор
notesstring?
пояснение для человека, не для логики.

Шаг-набор (set)

Отрезок — это список рабочих шагов и шагов отдыха. В текущих данных — set_repeats внутри шага с phase='set'.

Step {
  phase: 'set'
  dimension: 'distance'
  label: '3×800м с прогрессией 4:15 → 3:50'
  reps: 3
  set_repeats: [
    { phase:'work',     dimension:'distance', distance_m:800, target:{type:'pace', from:'4:15'} },
    { phase:'recovery', dimension:'distance', distance_m:250, target:{type:'hr', zone:'Z1', bpm:115} },
    { phase:'work',     dimension:'distance', distance_m:800, target:{type:'pace', from:'4:00'} },
    { phase:'recovery', dimension:'distance', distance_m:250, target:{type:'hr', zone:'Z1', bpm:115} },
    { phase:'work',     dimension:'distance', distance_m:800, target:{type:'pace', from:'3:50'} }
  ]
}

Инварианты

  • duration_min > 0 у каждого шага; сумма шагов = duration_min сессии.
  • Зона HR принадлежит Athlete.hr_zones — шаг не хранит границы зон, только zone и (опционально) bpm.
  • В наборе чередование work/recovery обязательно; нечётное число рабочих шагов.
  • Шаг с target.type='none' — разминка/заминка/мобилити.
  • Прогрессия внутри набора выражается pace.from → pace.to, а не двумя разными шагами.
Сильная сторона этой модели «3×800 с прогрессией 4:15 → 3:50» — это один шаг с полем прогрессии, а не три шага. Поэтому такой тренировкой можно управлять: сдвинуть прогрессию (4:15 → 4:05 → 3:45) — один параметр; сравнить с прошлой неделей — один параметр; понять, что изменилось — один diff вместо сравнения списков шагов.

06 Правила домена

Инварианты (нарушить нельзя)

  1. Сумма duration_min шагов = duration_min сессии.
  2. Зона шага ∈ Athlete.hr_zones.
  3. У сессии есть ≥ 1 шаг; у шага есть dimension и target.
  4. Каждая сессия недели принадлежит одному discipline и одному дню.
  5. Объём недели ≤ max_total_hours_per_week и ≥ min_total_hours_per_week.
  6. Каждая сессия с причиной изменения — только через Command с заполненным reason.
  7. Каждый шаг в наборе — либо work, либо recovery; набор начинается и заканчивается на work.
  8. Фаза недели определяется только season_week — не датой, не ISO-неделей.

Производные — вычисляются, не хранятся

  • Темпы шагов — от Athlete.vdot через таблицы Дэниэлса. Хранить строкой без ссылки на VDOT нельзя.
  • Границы HR-зон — от HRmax/RHR/LTH. Шаг знает только имя зоны.
  • Объём недели, интенсивность в % — из шагов.
  • Фаза недели — из season_week и диапазонов фаз.
  • Плановые километры по дисциплине — из шагов.
