Domain v0.2 — сезон, планы, тренировка

Корень — сезон. Внутри — цели и планы. План строится по модели плана. Неделя — высокий уровень. Тренировка — плоский список шагов.
v0.2 · перестройка по правкам от 25.10.2026
Что изменилось против v0.1 Корень — сезон, не цель. Цели живут внутри сезона. Появились Plan (несколько, параллельных) и PlanModel (Дэниэлс и прочие) отдельным описанием. Недели не детализируются заранее — только высокоуровневые намерения. Прогрессия развёрнута в плоский список шагов (работа + отдых, отдых — полноценный шаг). У шага обязательные: спорт · тип цели · величина цели · фокус.

00 Дерево модели

Пять уровней. Корневой — сезон: у него есть длина и цели. План — окно внутри сезона со своей логикой построения. Неделя внутри плана — намерение, не расписание. Тренировка — список шагов.

03 Plan — план

План — это окно внутри сезона, у которого есть свой срок, свой спорт, свой набор целей и своя модель построения. Не «фаза» (фаза — часть плана), а самостоятельная единица, которая может жить параллельно с другими.

Plan aggregate
Один план = один вид спорта + один набор целей + одна модель построения + свой срок.
idstring
plan_run_10k_2027
sportenum
run · bike · swim · strength · brick. Один план — один спорт. Это держит модель плана применимой.
goal_idsstring[]
список целей, которые план обслуживает. Многие-ко-многим: триатлон обслуживают три плана (бег, вело, плавание).
model_refstring
ссылка на PlanModel — логику построения. Для бега: daniels_run_v1.
start · enddate
срок плана. План короче сезона. Сейчас: run-план 11.10.2026 → 18.04.2027 (28 недель), потом триатлонная часть.
phasesPhase[]
фазы плана: {id, goal, focus, load_range, volume_range, intensity_pct_mean, deload_weeks}. run_base → run_build → run_specific → run_taper.
weeksWeek[]
недели плана — высокий уровень, без шагов (см. §07).
budgetobject

Но вторая половина сезона (триатлон, 21 неделя) не имеет модели построения ни для вела, ни для плавания — в weekly_macro это просто строки bike: '1×60м', swim: '1×30м'. Формально это один план, фактически — два, причём второй без логики.
04 Критика: параллельные или последовательные планы

Это развилка, которая меняет модель целиком. Разберу оба варианта честно.

Вариант A: три параллельных плана (бег, вело, бассейн)

Что ломается 1. Пересечение нагрузок. План по бегу, план по велу и план по плаванию каждый по отдельности проходят свои лимиты — но суммарно они могут превысить 11 ч/неделю, и никто этого не заметит. Лимит живёт в сезоне, а проверяется в плане.
2. Конфликт календаря. Вторник 18:00 — бег или вело? Решение принимает не план, а что-то выше. Планы не умеют делить слоты.
3. Плавание и вело без модели. У Дэниэлса есть только бег. Для плавания нужен другой подход (темп на 100 м, интервалы 400/800 по ощущениям). Второй и третий планы окажутся с пустой логикой — как сейчас в триатлонной половине сезона.
4. Дублирование недель. 3 плана × 49 недель = 147 недель с недельными рамками. Синхронизировать их — отдельная задача.
5. Потеря целостности триатлона. Триатлон — это один тренировочный процесс, а не три независимых. Переходы (кирпики) живут на стыке планов, и ни один план их не владеет.

Вариант B: два последовательных плана, ограниченных целями

Что ломается 1. Триатлон всё равно параллелен внутри себя. План «триатлон» должен одновременно вести бег, вело и плавание. Последовательность тут не помогает — внутри плана нужны подпланы по спорту, то есть возвращаемся к варианту A, но вложенный.
2. Некуда деть параллельные виды спорта. Если завтра будет третья цель (например, веломарафон в мае) — последовательная схема её не влезет без разбора season.
3. Граница «по цели» — искусственная. Цель заканчивается 18.04, но триатлонная подготовка начинается не в этот день, а раньше, и параллельно идёт с бегом. Реальность — перекрытие, а не очередь.

Что предлагаю: планы пересекаются, но не наезжают

Модель, которая закрывает оба случая Сезон — контейнер (длина, цели, гонки, правила, лимиты). Внутри — планы, каждый со своим сроком, спортом, набором целей и моделью. Планы могут пересекаться по времени; запрещено ровно одно: две недели одного и того же спорта в один season_week не могут принадлежать разным планам. Всё остальное — легально.
СвойствоКак обеспечивается
Нет двойного бронированияинвариант: (спорт, season_week) → не более одного плана
Нет перегрузки по суммелимиты живут в сезоне; план отдаёт «запрос», сезон раздаёт бюджет
Слот дня не конфликтуеткалендарь — общий слой, планы заявляют намерения, арбитраж выше
Цель обслуживают несколько плановgoal_ids — список, а не ссылка
Модель плана подставляетсяmodel_ref на план: у бега — Дэниэлс, у плавания — свой

Что это даёт для текущего сезона

  • Один беговой план 11.10.2026 → 18.04.2027 под цель g_run_spring, модель daniels_run_v1.
  • Планы триатлона — либо три отдельных (бег/вело/плавание) со своей логикой, либо один план-триатлон с тремя подпланами. Второй вариант честнее: переходы и кирпики — общие.
  • Сезон держит правило: суммарно ≤ 11 ч/нед, ≤ 30 % интенсивности, приоритет целей 60/40.
Где я не уверен «План = один спорт» — ограничение, которое сильно упрощает, но может не подойти для кирпиков и для силовой работы внутри триатлонного плана. Компромисс: разрешить плану объявлять secondary_sports, но тогда модель плана должна уметь работать с чужим спортом — а Дэниэлс не умеет. Решать при появлении кирпиков.
05 PlanModel — логика построения

Модель плана — это правила, по которым из цели, профиля и фазы получается неделя и тренировка. План ссылается на модель, но не содержит её. Описание модели хранится отдельно — и это то, что ты просил детализировать.

PlanModel strategy
Контракт поведения. Реализация может быть любой; описание — одно на модель.

intensity_mapmap

intensity_unitsenum[]
на чём задаётся интенсивность: pace · hr · power · rpe
block_rulesobject
правила блоков: {repeat_unit, rest_min, rest_distance_m, distance_m, min, max, label}
progression_rulesobject

Почему описание отдельно от реализации Модель — это код (таблицы, правила). Описание — это документ: «Дэниэлс = темпы от VDOT, интенсивность по зонам, объём растёт на 5 % в неделю, разгрузка каждую 4-ю». Описание читает человек, когда решает, подходит ли модель его задаче. Оно же — основание для выбора модели в UI: список моделей с описаниями, а не с названиями.
06 Дэниэлс — детально

Это единственная реализованная модель, поэтому разбираю её полностью — как образец того, что должно быть в описании каждой модели.

daniels_run_v1 описание
Источник: Daniels' Running Formula, скан таблиц, принесён 24.10.2026. Лежит в ~/coach/reference/daniels/: сырые txt + разобранный json + обвязка lib/daniels.py.

Вход

  • VDOT — единственное число, из которого выводится всё остальное. Сейчас 47 (заявлено) / 46.4 (по факту 10К 44:06).
  • HRmax 182 · RHR 54 · LTH 164 — для привязки к HR-зонам атлета.
  • Цель — время на дистанции; обратным ходом даёт целевой VDOT (10К 40:00 → VDOT 52).

Дыра в мосте зон У атлета 7 зон, у Дэниэлса 5. Зона Z6 (169–172, super-threshold) не имеет источника в Дэниэлсе: Пв начинается от 182 (100 % HRmax), а И кончается там же. Между Z5 (до 168) и Z7 (с 173) — пусто. При этом именно Z6 стоит в шаблоне vo2max (work_zone: Z6, hr_target: 172). То есть целевая зона VO2max-сессии лежит в дыре, которую никто не заполнил. Это надо решить: либо Z6 получает долю VO2max явно (например 93–95 %), либо шаблон vo2max переводится на И (Z7).

Правила объёма

  • Рост объёма: ≤ +10 % в неделю, шаг 3 недели, deload каждую 4-ю.
  • Guard качественных сессий: объём работы новой интервальной сессии ≥ 0.9 × объёма последней интервальной за 21 день. Сейчас: последняя 3070 м → порог 2763 м.
  • Выбор варианта — по паре (адаптационная цель, масштаб): light / medium / heavy / peak.

Чего модель не умеет

  • Только бег. Вел и плавание — вне модели.
  • Нет силовой работы и мобильности.
  • Нет работы с расписанием, окнами и ресурсами — это календарный слой, не модель.
  • Нет учёта веса, сна, травм, настроения.
  • Темпы привязаны к VDOT: без свежего VDOT вся таблица устаревает целиком.

Каталог качественных сессий

11 адаптационных целей: vo2max · threshold_speed · threshold_power · tempo · mixed · pyramid · fartlek · progression · time_trial · taper_race_pace (+ сезонные варианты). У каждой — свои варианты по масштабу. Это отдельный справочник, а не часть модели плана, но модель на него ссылается при выборе структуры.

07 Week — неделя без деталей

08 Workout — тренировка

Тренировка = список шагов, повторы развёрнуты

Никаких вложенных set_repeats и никакой «прогрессии» как отдельного объекта. Повтор — это несколько шагов подряд: работа, отдых, работа, отдых. Отдых — такой же шаг, у него свой объём и свой фокус.

warmup work rest cooldown transition
Что меняется и почему это лучше Прогрессия 4:15 → 4:00 → 3:50 — это три отдельных шага, у каждого свой темп. А не «один шаг с полем прогрессии». Итог: список шагов — единственный источник правды о структуре, любой шаг редактируется независимо, сравнение двух тренировок = сравнение плоских списков, а «3×800» восстанавливается из шагов обратно для показа.
Цена: шаблон, который генерирует повторы, тоже должен быть плоским (или уметь разворачиваться в плоский). Это честнее: шаблон отвечает за «как строим», развёрнутый список — за «что делаем».
09 Step — шаг

Минимальный набор, который ты назвал: спорт · тип цели · величина цели · фокус. Плюс роль шага и, для отдыха, — свой объём.

Step value object
Одно выполнимое действие. В шаге нет ничего предметного, кроме объёма и фокуса.
roleenum
warmup · work · rest · cooldown · transition
sportenum
run · bike · swim · strength. Спорт обязателен: в неделе бывают разные, внутри тренировки — один, но лучше явно.
target_typeenum
Время или расстояние — а что ещё? См. список ниже.
target_valuenumber
величина: 5 минут · 3 км · 800 м · 400 м. Единица задаётся типом, отдельного поля unit не нужно.
focusenum
Темп или ЧСС — и дальше: pace · hr · power · rpe · none
focus_valueobject?
что именно: {pace:'4:15'} · {hr_zone:'Z5', hr_cap:172} · {power_w:260}. Может отсутствовать: фокус есть, а значения ещё нет — оно вычислится из профиля.
labelstring?
«800 м @ 4:15» — человекочитаемо, генерируется, но может быть задано вручную.
notesstring?
пояснение для человека.

Типы цели: время, расстояние — и что ещё

target_typeЕдиницаКогда нуженПример
timeминвсё, что меряется часамиразминка 15 мин · отдых 2 мин
distanceм / кмотрезки, длинная, плавание800 м · 14 км
lapsштукибассейн: круги по дорожке8 кругов по 400 м
repsштукисиловая: повторы упражнения3×45 с планка
open—свободная тренировка без заданного объёма«плавание на свободной скорости»
Единица темпа зависит от спорта Для бега темп — на километр, для плавания — на 100 м, для вела — на километр. Если хранить focus_value.pace строкой «4:15», то в бассейне «1:35» — это 100 м или километр? Нужно либо хранить темп в секундах на метр, либо добавлять pace_basis в шаг: {pace:'1:35', per:'100m'}. Иначе шаг из разных видов спорта нельзя сравнивать и нельзя валидировать.

Отдых — полноценный шаг

У отдыха своя величина и свой фокус. Сейчас в данных отдых задаётся двумя полями внутри блока (rest_min и rest_distance_m) — это две разные величины в одном месте, и непонятно, что считается основным. В модели отдых — обычный шаг: role:'rest', target_type:'distance', target_value:250, focus:'hr', focus_value:{hr_zone:'Z1'}.

Инварианты шага

  • В шаге есть спорт, тип цели, величина и фокус.
  • Величина > 0; для open величина не задаётся.
  • focus_value соответствует focus: hr → зона атлета, pace → темп с базой, none → значения нет.
  • Шаги внутри тренировки не пересекаются по времени: сумма длительностей = длительность тренировки.
  • Отдых после последней работы — опционален (между блоками может быть длинный переход).

11 Правила домена

Инварианты (нарушить нельзя)

  1. Сезон: цели внутри, планы внутри, у каждого плана свой срок ⊂ сезон.
  2. План: один спорт, одна модель плана, ноль или больше целей.
  3. Инвариант параллельности: (спорт, season_week) принадлежит не более чем одному плану.
  4. Модель плана заявлена для спорта плана: model.sports ⊇ {plan.sport}.
  5. Неделя принадлежит ровно одному плану; её focus — одна адаптационная цель.
  6. Тренировка: спорт, kind, focus, objective, шаги.
  7. Шаг: роль, спорт, тип цели, величина, фокус. Величина > 0 (кроме open).
  8. Сумма длительностей шагов = длительность тренировки.
  9. Шаги тренировки не пересекаются, отдых идёт после работы.
  10. Зона шага ∈ HR-зонам атлета.
  11. Детализация недели помечена версией входов; устаревшая — помечается, а не показывается молча.
  12. Изменение плана — только через Command с причиной.

Производные — считаются, не хранятся

  • Темпы шагов — от VDOT через модель плана. Строка темпа без ссылки на inputs_version — недопустима.
  • Границы HR-зон — от HRmax/RHR/LTH.
  • Длительность тренировки, дистанция, объём работы — из шагов.
  • Объём недели и интенсивность в % — из намерений и шагов.
  • Фаза недели — из season_week и диапазонов фаз плана.
